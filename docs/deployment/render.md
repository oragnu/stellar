# Deploying to Render

Render runs Stellar's existing `docker/Dockerfile` unchanged. You need a
Render web service, a Render Postgres database and a handful of
environment variables. A `render.yaml` Blueprint at the repo root sets up
both resources in one step.

Render has a free tier that is good for **testing** Stellar, but not for
running it long term: the free database is deleted after 30 days (see
[Free tier: what to expect](#free-tier-what-to-expect)). For a deployment
you intend to keep, use paid plans for both the web service and the
database. The setup steps are identical, only the `plan` values change.

> **Not yet validated against a real deploy.** This recipe was written
> from Render's documentation and the app's requirements, the same way the
> Fly.io and bare-metal recipes were. Railway is still the only target
> exercised end to end. Update this note (and `docs/plan.md`) once a real
> Render deploy has been run.

## Option A: Blueprint (recommended)

1. Fork or push this repo to a GitHub account Render can access.
2. In the Render Dashboard: **New → Blueprint**, pick the repo. Render
   reads `render.yaml` and proposes two resources: a `stellar` web service
   (Docker, free plan) and a `stellar-db` Postgres database (free plan).
3. Render prompts for the variables marked `sync: false` in `render.yaml`.
   Fill in what you have now; you can't know `BASE_URL` until the service
   has a URL, so set a placeholder and fix it in step 5:
   - `SECRET_KEY` and `SECRET_ENCRYPTION_KEY` are generated by the
     Blueprint; no input needed. (The app derives its Fernet key from
     `SECRET_ENCRYPTION_KEY` in `backend/app/services/crypto.py`, so any
     random string works.)
   - `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET`: from the OAuth App in
     step 6. A placeholder is fine for now.
   - `DATABASE_URL`: see step 4.
   - `BASE_URL`: placeholder for now.
4. **Set `DATABASE_URL` with the `postgresql+asyncpg://` scheme.** Open
   the `stellar-db` database in the Dashboard, copy its **Internal
   Database URL**, and change the scheme from `postgresql://` to
   `postgresql+asyncpg://`:
   ```
   postgresql+asyncpg://<user>:<password>@<host>/<database>
   ```
   Render's URL uses plain `postgresql://`, which SQLAlchemy maps to the
   synchronous `psycopg2` driver. Stellar only installs `asyncpg`, so an
   unmodified URL fails at startup. This is the same issue as Railway's
   and Fly's default URLs. It's also why `render.yaml` can't wire the
   database in with `fromDatabase`: that injects the URL as-is. Use the
   **internal** URL (it stays on Render's private network and needs no
   TLS settings), not the external one.
5. Once the service has deployed, copy its URL
   (`https://<service-name>.onrender.com`) into `BASE_URL`, with no
   trailing slash.
6. Create the GitHub OAuth App at
   `https://github.com/settings/applications/new`:
   - **Homepage URL**: `https://<service-name>.onrender.com`
   - **Authorization callback URL**:
     `https://<service-name>.onrender.com/api/v1/auth/github/callback`
   - **Enable Device Flow**: leave unchecked.

   Put the client ID and secret into `GITHUB_CLIENT_ID` /
   `GITHUB_CLIENT_SECRET`.
7. Saving environment variables triggers a redeploy. Migrations run
   automatically at container start (`docker/entrypoint.sh`), the same as
   every other recipe. Visit the URL and sign in with GitHub.

## Option B: Manual setup

1. **New → Postgres**: name `stellar-db`, database `stellar`, user
   `stellar`, plan **Free** (testing) or a paid plan. Use the same region
   you'll pick for the web service.
2. **New → Web Service**: connect the repo, then:
   - **Language / Runtime**: Docker
   - **Dockerfile Path**: `./docker/Dockerfile`
   - **Docker Build Context Directory**: `.` (the repo root; the
     Dockerfile copies from both `backend/` and `frontend/`)
   - **Instance Type**: Free (testing) or a paid type
   - **Health Check Path**: `/api/v1/health`
3. Add the environment variables in the table below, then follow steps
   4–7 of Option A.

## Environment variables

| Variable | Value | Why |
|---|---|---|
| `PORT` | `8000` | The container always listens on 8000 (`docker/Dockerfile`'s `CMD`). Render's default `PORT` is 10000; setting it to 8000 tells Render where to route traffic, so it doesn't have to detect the port. |
| `FORWARDED_ALLOW_IPS` | `*` | Lets gunicorn/uvicorn trust Render's proxy headers so the app sees real client IPs. Without it, every request appears to come from Render's proxy, so all visitors share one rate-limit bucket (120 req/min) and sessions record the proxy's IP. Safe here because only Render's proxy can reach the container. |
| `DATABASE_URL` | `postgresql+asyncpg://…` (internal URL) | See Option A, step 4. |
| `BASE_URL` | `https://<service-name>.onrender.com` | Used to build the OAuth callback and post-login redirect. Must match the OAuth App exactly. |
| `SECRET_KEY` | `openssl rand -hex 32` | Generated automatically by the Blueprint. |
| `SECRET_ENCRYPTION_KEY` | Any random string, e.g. `openssl rand -hex 32` | Generated automatically by the Blueprint. Encrypts stored GitHub tokens. **Don't change it after first login**, or stored tokens can no longer be decrypted. |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | From the OAuth App | |
| `APP_ENV` | `production` | |
| `SESSION_COOKIE_SECURE` | `true` | Render serves everything over HTTPS. |

The remaining settings in `.env.example` (`CACHE_BACKEND=db`,
`RATE_LIMIT_STORAGE_URI=memory://`, `SCHEDULER_ENABLED=true`, …) default
to the right values for a single Render instance and don't need setting.

## Deploys

Render redeploys automatically on every push to the connected branch.
Under the service's **Settings → Build & Deploy → Auto-Deploy**, choose
**After CI Checks Pass** so a push to `main` only deploys once
`backend-ci`, `frontend-ci` and `e2e` are green.

To stop deploys (for example, when pausing a test instance), set
Auto-Deploy to **Off** or suspend the service. That's cleaner than
removing the repo from Render's GitHub App, which disconnects every
Render service that uses it.

## Free tier: what to expect

Fine for trying Stellar out; each of the following matters before relying
on it:

- **The free database is deleted after 30 days.** Free Render Postgres
  databases expire 30 days after creation. After that you have 14 days to
  upgrade to a paid plan before Render deletes the database and all its
  data. Free databases also have **no backups** and a 1 GB storage cap
  (plenty for a single user's stars, tags and notes). You can have one free
  database per workspace.
- **The web service sleeps after 15 minutes without traffic.** The next
  request wakes it, which takes about a minute. Each wake also runs
  `wait_for_db` and `alembic upgrade head` (a few seconds when no new
  migrations are pending). If you land on the GitHub OAuth callback while
  the service is waking, the redirect will be slow but still completes.
- **Background jobs mostly won't run.** APScheduler runs in-process (see
  `docs/adr/0003-apscheduler-no-redis-by-default.md`), and its intervals
  (star sync every 4 h, cache eviction hourly, session cleanup every 6 h)
  restart from zero every time the service wakes. On an instance that
  sleeps after 15 idle minutes they rarely fire. Nothing breaks: stars are
  re-synced on demand when the cache is older than `STAR_CACHE_TTL_HOURS`,
  but expired cache rows and sessions are cleaned up less often. A paid
  instance doesn't sleep, so the jobs run normally there.
- **Small instance**: 512 MB RAM and 0.1 CPU. Stellar runs a single
  gunicorn worker, which fits. The first sync for an account with many
  stars is slow even on a larger instance (about 90 seconds for 788 stars
  on Railway); expect it to take longer at 0.1 CPU.
- **Monthly hours**: free services share 750 instance-hours per workspace
  per month, and sleeping services don't use any. One Stellar instance
  fits comfortably.

## Moving to a paid production deployment

- Change both plans: the web service to a paid instance type (no
  spin-down, so the scheduler runs on its intervals) and the database to a
  paid plan (no expiry, with backups). In `render.yaml`, that's the two
  `plan:` values.
- Upgrade the free database **before day 30**, or `pg_dump` it and
  restore into the new paid database.
- **Keep the web service at one instance.** APScheduler assumes a single
  process, so a second instance would run every job twice. Same rule as
  the Fly.io and Railway recipes.
- Add a custom domain under **Settings → Custom Domains** (Render issues
  the TLS certificate), then update `BASE_URL` and the OAuth App's URLs to
  match.
